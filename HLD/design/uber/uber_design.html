Uber / Ola — System Design

FAANG SDE2 Cheat Sheet

Overview

Core Opening Insight This is a location-heavy write system at heart. The central design challenge is not "how to store rides" — it's "how to index 500K moving driver locations in real time and query them by geography in under 100ms." Separate stateful services (Location, Matching) from stateless services (Auth, Fare, Profile) from day one.

Functional Requirements

Core (In Scope)

  • Rider books a ride from current location
  • System finds nearest available driver
  • Real-time driver location on rider screen
  • Ride lifecycle: request → match → pickup → drop
  • Fare calculation at end of trip
  • Rider/Driver profiles with ratings
  • Ride history for both rider and driver

Miscellaneous (Mention, Don't Design)

  • Surge/dynamic pricing
  • Scheduled rides
  • Carpooling / shared rides
  • Driver payments / settlements
  • In-app chat between rider and driver
  • Route navigation

Non-Functional Requirements

Latency

  • Driver matched within 5 seconds of booking
  • Location update visible in <2 seconds
  • Fare returned within 1 second of trip end

Scale + Reliability

  • Handle peak metro-city load (office hours)
  • Matching failure → queue, not error
  • Driver disconnect → graceful degradation
  • No double assignment of same driver

Out of Scope

ML-based demand forecasting, driver earnings dashboard, compliance/background checks, route optimization engine (use Google Maps API), multi-city fleet management, fraud detection.

Stateful vs Stateless Split — State This Early Location Service is the only stateful service — it maintains persistent WebSocket connections per driver. Matching Service is stateless — reads Redis, writes PostgreSQL, any pod handles any request. Auth, Fare, Profile, Trip Service are all stateless. Mixing these will kill your scale story.
Red Flag Never start designing before asking: "Are we designing just the matching flow, or full lifecycle including payments?" Scope this in the first 60 seconds. A SDE1 starts drawing boxes immediately.

Capacity Estimation

Always Show Your Math State assumptions first. Then derive. Never guess a number without showing how you got there.

Assumptions

DAU (total)       : 10M  (9.5M riders + 500K drivers)
Active drivers    : 500K at peak (6 PM weekday in metro cities)
Rides per rider   : 2 per day
Location update   : every 4 seconds per driver

Ride Request QPS

Total rides/day   = 10M riders × 2 rides = 20M rides/day
Spread over 18hrs = 20M / (18 × 3600)
                  = 20,000,000 / 64,800
                  ≈ 308 ride requests/sec

Peak multiplier (2x) → ~600 ride requests/sec at office hours

Location Write QPS — The Critical Number

Active drivers    = 500,000
Update frequency  = 1 update every 4 seconds

Location writes/sec = 500,000 / 4 = 125,000 writes/sec = 125K/sec

This is your main bottleneck argument.
PostgreSQL max    ≈ 40K writes/sec (ideal conditions, single node)
125K >> 40K → SQL is dead on arrival for location storage.

Location Read QPS

Active concurrent rides (Little's Law):
  Arrival rate × Avg duration = 500 rides/sec × 1200sec (20 min avg)
                              = 600K concurrent rides

But NOT all riders read location — only those in DRIVER_EN_ROUTE state:
  State 1 REQUESTED (30s)    → 600K × (30/1200)  ≈ 15K riders
  State 2 DRIVER_EN_ROUTE (5min) → 600K × (300/1200) ≈ 150K riders ← active readers
  State 3 IN_PROGRESS (15min) → rider in cab, not watching screen

Active readers ≈ 150K
Location reads/sec = 150,000 / 4 = 37,500 ≈ 40K reads/sec

Write : Read = 125K : 40K = 3:1 → write-heavy
→ Confirms Redis (in-memory, write-optimized) as the right choice.

Storage Estimation

--- Ride History ---
Rides/day             = 20M
Record size per trip  ≈ 500 bytes (pickup, dropoff, route, fare, IDs)
Daily storage         = 20M × 500B = 10 GB/day
Annual                = 10 GB × 365 = 3.65 TB/year

--- Driver Location (Redis, ephemeral) ---
Per driver entry      ≈ 64 bytes (driver_id + lat + lng + TTL metadata)
Total active drivers  = 500K
Redis memory needed   = 500K × 64B ≈ 32 MB  ← trivial, fits in single Redis node

--- Trip (PostgreSQL, active only) ---
Active trips at peak  ≈ 100K
Per record            ≈ 2 KB
Active DB size        ≈ 200 MB  ← easily fits in memory
Why SQL Dies at 125K Writes/Sec SQL uses B-Tree indexes on disk. Every location update = index update = disk I/O. At 125K writes/sec, even with SSDs and tuning, a single PostgreSQL node saturates. More critically, location data is ephemeral — it's useless after 30 seconds. Paying for ACID, joins, and indexes on data you throw away is the wrong tradeoff. Redis GEO is in-memory, has native geo-commands, and handles 125K writes/sec on a single node.

Protocol Deep Dive

The Core Decision HTTP polling fails at 125K writes/sec. WebSocket solves bandwidth but introduces statefulness. Everything after this is consequence management.

Polling vs Long Polling vs WebSocket

ProtocolHow it worksExact failure reason for location
HTTP PollingRider/Driver hits endpoint every N seconds500K drivers × 1 req/4s = 125K req/sec of pure overhead. Each HTTP request = TCP setup + auth + headers. At 500K drivers on 4s interval, this is 125K new connections/sec — server collapses under handshake cost alone.
Long PollingServer holds connection open until data availableRound-robin load balancer sends reconnect to a different server. Server 2 has no context for this driver's session. Breaks routing — you'd need sticky sessions, and sticky sessions break horizontal scaling.
WebSocketPersistent bidirectional TCP connectionDriver opens one connection. Location updates flow through it continuously. Zero reconnect overhead. Server pushes to rider app same way. Winner.
The Statefulness Cost — Always Mention This WebSocket connections are stateful. The same driver MUST always hit the same Location Service instance. This requires sticky sessions at the load balancer (based on driver_id hash) OR a connection registry in Redis so any instance can route to the right connection owner. This is the tradeoff you must articulate.

Redis Connection Registry

Key   : driver:{driver_id}:connection
Value : location_service_pod_id
TTL   : 30s (reset on each heartbeat)

Why Redis not Zookeeper?
→ Redis: sub-ms reads, purpose-built KV, TTL support native
→ Zookeeper: consensus protocol, ~10ms reads, built for leader election
   Using ZK for per-request routing lookup = 10ms added to every location update
   = 125K × 10ms = 1250 server-seconds of wasted latency/sec

Zookeeper's Actual Role

Zookeeper is used ONLY at login time for service discovery:
  → Driver logs in → hits API Gateway → ZK tells it which
    Location Service instances are alive → driver connects to one
  → ZK is NOT queried per location update
  → ZK watches for Location Service instance health (liveness)

Heartbeat Mechanism

Driver sends heartbeat ping every 4s (same as location update)
Redis TTL on driver key = 30s

Why not 1s heartbeat?
  → 500K drivers × 1 ping/sec = 500K Redis writes/sec
  → Current: 500K/4 = 125K Redis writes/sec
  → 4x reduction in Redis load for same fault detection latency

Zombie connection problem:
  → Driver app crashes without clean close (network drop, OOM kill)
  → TCP connection hangs on server (server doesn't know yet)
  → Redis TTL expires after 30s → driver key gone → auto-offline
  → No manual cleanup needed. TTL IS the offline signal.
Multi-Pod Deployment — DB-Level Locking Application-level sequential processing works on a single pod. With 10 Location Service pods, two pods can receive two ride requests for the same driver simultaneously. Application code cannot see each other's state. Only DB-level SELECT FOR UPDATE on the driver row guarantees mutual exclusion. This is the multi-pod inventory safety rule.

Redis GEO Schema

GEOADD  drivers:active  {longitude}  {latitude}  "{driver_id}"
TTL     driver:{driver_id}  30  (reset on each heartbeat)

GEORADIUS drivers:active  {rider_lng}  {rider_lat}  5  km
          ASC COUNT 10   → sorted by distance, top 10

Geohash precision used internally: length 6 ≈ 1.2km cells
→ Good enough for city-level matching
→ Query current cell + 8 surrounding cells to handle boundary edge cases

PostgreSQL — Trips Schema

CREATE TABLE trips (
  trip_id       BIGINT PRIMARY KEY,   -- Snowflake ID
  rider_id      BIGINT NOT NULL,
  driver_id     BIGINT NOT NULL,
  status        VARCHAR(20),          -- REQUESTED|MATCHED|IN_PROGRESS|COMPLETED
  pickup_lat    DECIMAL(10,7),
  pickup_lng    DECIMAL(10,7),
  dropoff_lat   DECIMAL(10,7),
  dropoff_lng   DECIMAL(10,7),
  fare          DECIMAL(10,2),
  created_at    TIMESTAMP,
  completed_at  TIMESTAMP
);

-- Critical index for driver assignment safety
SELECT * FROM trips WHERE driver_id = ? AND status = 'IN_PROGRESS'
FOR UPDATE;  -- prevents concurrent assignment of same driver

Cassandra — Ride History Schema

CREATE TABLE ride_history (
  user_id       BIGINT,
  year_month    TEXT,         -- '2024-01' — time bucketing
  trip_id       BIGINT,       -- Snowflake (sortable by time)
  driver_id     BIGINT,
  pickup_loc    TEXT,
  dropoff_loc   TEXT,
  fare          DECIMAL,
  rating        INT,
  PRIMARY KEY ((user_id, year_month), trip_id)
) WITH CLUSTERING ORDER BY (trip_id DESC);

Partition key: (user_id, year_month)
→ Distributes load across nodes. Single user's entire history
  in one partition = hot spot. year_month bucketing avoids this.

Clustering key: trip_id DESC
→ Most recent trips returned first without sorting overhead

Trip ID — Why Snowflake

Option 1: UUID (random) → not sortable, no time info, index fragmentation
Option 2: created_at    → server-side clock drift 10-100ms across pods
                         → two trips at same ms = ambiguous ordering
Option 3: Snowflake ID  → 41-bit timestamp (ms precision)
                         → 10-bit machine ID
                         → 12-bit sequence (4096 IDs/ms/machine)
                         → globally unique, time-sortable, cross-server ordering = best-effort
Two-Tier Trip Storage PostgreSQL holds ACTIVE trips only (currently in-progress or completed within last 24hrs). A background job moves COMPLETED trips to Cassandra. This keeps PostgreSQL lean — ~100K active trips at peak = 200MB. PostgreSQL never grows unboundedly.

Matching Algorithm — Step by Step

1
Get rider lat/lng from booking request
↓
2
GEORADIUS query on Redis — sorted by distance ASC, fetch top 10 within 5km
↓
3
Filter: remove drivers with status = "on_trip" (Redis flag or PostgreSQL check)
↓
4
Bonus inclusion: drivers whose current trip ends within 2 mins and are nearby (improves matching rate)
↓
5

↓

↓
7

↓
8

Timeout Handling

No driver accepts within 30s:
  Tier 1: 2km → wait 30s
  Tier 2: 5km → wait 30s
  Tier 3: 10km → wait 30s
  Tier 4: city-wide → wait 60s → queue rider, notify when driver available

Failure Points + Fixes

#Failure PointFix
1Driver accepts but network drops before server gets ACKIdempotency key on accept request (trip_id + driver_id). Retry safe — second accept is no-op if trip already matched.
2Two drivers accept simultaneously (race condition)SELECT FOR UPDATE on trip row in PostgreSQL. Second driver's transaction waits, sees status = MATCHED, returns "ride already taken".
3Matching Service crashes mid-dispatchRide requests published to Kafka before dispatch. On recovery, Matching Service consumes from queue. No lost requests. Rider sees "Finding your ride..."
4No drivers in any radius tierRider added to waiting queue (Redis sorted set by wait time). When driver becomes available nearby, dequeue and attempt match.
5Payment Service down at trip completionTrip marked COMPLETED. Payment event queued in Kafka. Retried with exponential backoff. Idempotency key = trip_id prevents double charge.
Why Top 3 Simultaneously, Not Sequential Sequential dispatch: send to driver 1, wait 15s for decline, then send to driver 2 = 30-45s total for a match. Simultaneous dispatch to top 3: first to accept = matched, others cancelled. Rider gets match in <5s. Tradeoff: slightly more notifications sent, but dramatically better user experience.

Geo-Indexing Strategies

This is the Core Technical Differentiator Every Uber system design question will probe how you index geography. Know Geohash deeply. Know QuadTree as a named tradeoff. Don't confuse them.

Geohash vs QuadTree

GeohashQuadTree
What it isEncodes lat/lng into a base32 string. Proximity = shared string prefix. "ttmf" and "ttmg" are adjacent cells.Recursively subdivides the map into 4 quadrants. Subdivides further where density is high.
StrengthSimple, Redis-native (Redis GEO uses Geohash internally). Prefix queries = fast proximity search.Handles uneven driver density. Mumbai CBD vs rural Maharashtra get different cell sizes automatically.
WeaknessCell boundary problem: two drivers 50m apart on opposite sides of a cell boundary have no shared prefix — GEORADIUS misses one unless you query 9 cells.Complex to build and maintain. Not available as a primitive in Redis or any standard DB. Custom implementation required.
SDE2 choiceUse Geohash + Redis GEOMention as known tradeoff

Geohash Precision Table

Length  Cell size     Use case
  4       ~40km × 20km  Country-level
  5       ~5km  × 5km   District-level
  6       ~1.2km × 0.6km  City-block level  ← Use this for ride matching
  7       ~150m × 75m   Street-level

Cell Boundary Fix

Problem: Driver at edge of cell A, Rider at edge of adjacent cell B
         → GEORADIUS on cell A misses the driver in cell B

Fix: Query current cell + 8 surrounding cells
     GEORADIUS already handles this — it queries by radius, not by cell
     The "9 cell" problem is only if you use raw Geohash prefix matching.
     With Redis GEORADIUS, you specify radius in km → it handles boundaries.

Write Amplification

500K drivers × 1 update/4s = 125K Redis GEO writes/sec

Redis handles this on a single node (Redis benchmark: 200K+ ops/sec on commodity hardware).
Add Redis Cluster for horizontal scaling if needed.
Each GEOADD is O(log N) where N = number of drivers in the sorted set.
At 500K drivers: log2(500K) ≈ 19 operations → still sub-ms.
Common Mistake Saying "Google Maps API for matching." Google Maps is for route calculation and ETA (external dependency). It cannot index 500K live driver locations or do sub-ms proximity queries. The geo-indexing of drivers is your system's responsibility. Never outsource the core technical problem.

Surge Pricing

Mention in requirements as out of scope for deep design, but know how it works at a component level.

SDE2 Framing "Surge pricing is essentially a real-time demand/supply ratio calculator per geographic cell. I'd keep it as a separate Fare Service responsibility with a cached surge multiplier per geohash cell."

How Surge is Computed

Demand  = active ride requests in geohash cell (last 5 mins)
Supply  = available drivers in geohash cell (Redis GEO count)

Surge ratio = Demand / Supply

Multiplier tiers:
  ratio < 1.5  → 1.0x (no surge)
  1.5 – 2.5   → 1.5x
  2.5 – 4.0   → 2.0x
  > 4.0        → 2.5x (capped)

Where Surge Lives

Fare Service queries:
  1. Redis GEO COUNT in 5km radius of pickup → driver supply
  2. Trip Service → pending ride requests in area → demand
  3. Computes ratio → looks up multiplier table
  4. Caches result: surge:{geohash6}  TTL=30s

On next fare request for same cell → cache hit, no recompute
Background job refreshes cache every 30s per active geohash cell

Failure Handling

Surge cache stale during sudden spike:
  → Rider pays 1.0x for ~30s until cache refreshes
  → Acceptable — eventual consistency is fine for pricing
  → Not financial data, no ACID needed here

Surge cache miss (Redis restart):
  → Default to 1.0x multiplier
  → Background worker repopulates within 30s
Out of Scope for SDE2 ML-based surge prediction, city-level demand forecasting, driver incentive programs during surge, regulatory surge caps by city. Mention these exist but don't design them unless asked.

Cancellation Fee Logic

Rider cancels AFTER driver en route (> 2 mins into en route):
  → Fare Service: cancellation_fee = base_fee (₹50 typically)
  → Trip marked CANCELLED with cancellation_fee recorded
  → Payment Service charged asynchronously via Kafka

Driver cancels after match:
  → No fee to rider
  → Cancellation logged, affects driver's cancellation rate metric
  → Auto-re-match if within 5 mins of original request

Failure Scenarios

FAANG expects 2-3 failures handled. Scoring bonus for detection + mitigation both covered.

Failure 1 — Driver App Crashes Mid-Ride

Detection: Location Service detects no WebSocket heartbeat for 30s. Redis TTL on driver location key expires.

Mitigation: Last known location cached and displayed to rider. Trip stays IN_PROGRESS (no auto-cancel — driver may reconnect). Grace period: 30s to reconnect. If reconnects → resumes normally. If not → if trip not started, discard driver and re-match. If trip in progress → flag trip for manual review + GPS reconstruction from last known state.

Failure 2 — Matching Service Crashes

Detection: Zookeeper health check on Matching Service instances. API Gateway returns 503 if all instances down.

Mitigation: Ride requests published to Kafka before Matching Service processes them. On service recovery, consumer group picks up from last committed offset. Rider sees "Finding your ride..." — not an error. No lost requests. Kafka retention = 24hrs buffer.

Failure 3 — Redis GEO Data Lost (Node Restart)

Detection: Redis restart event. Location Service connection pool gets reset.

Mitigation: Drivers re-register location on next heartbeat ping (within 4s). 4-second recovery window per driver. Brief matching gap acceptable — ride requests during this window get queued in Kafka and retried. Enable Redis AOF persistence to minimize data loss on restart. Alternatively, Redis Cluster with replication.

Failure 4 — Payment Service Down at Trip Completion

Detection: Fare Service gets timeout/500 from Payment Service.

Mitigation: Trip marked COMPLETED in PostgreSQL (trip state is separate from payment state). Payment event published to Kafka with idempotency key = trip_id. Payment Worker retries with exponential backoff (1s, 2s, 4s, 8s... up to 24hrs). Rider sees "Payment processing" in app. Double-charge prevented by idempotency key — retries are safe.

Failure 5 — No Drivers in Any Radius

Detection: Matching Service gets 0 results after all radius expansion tiers exhausted.

Mitigation: Rider added to waiting queue (Redis sorted set, key = geohash, score = timestamp for FIFO). When any driver in the area completes a trip or comes online → trigger match attempt against queue. Rider receives ETA notification ("No drivers nearby. We'll notify you when one becomes available.") Don't fail immediately — demand spikes resolve within minutes.

Failure Anti-Pattern Never say "the system fails gracefully." Explain exactly HOW it fails gracefully: what detects the failure, what the user sees, how state is preserved or recovered, and what prevents data loss or double-processing.

Q&A — Interview Flashcards

Click to reveal answer. These are the exact questions FAANG interviewers ask after you finish your design.

1. Why Redis GEO over PostGIS for driver location? ›
Three reasons: (1) In-memory — sub-ms reads and writes vs ~10ms for disk-based PostGIS. At 125K writes/sec, the 10ms latency compounds to 1250 server-seconds of added wait per second. (2) Native TTL — Redis auto-expires stale driver keys after 30s. PostGIS needs a cron job to clean stale rows. (3) Location data is ephemeral — 30-second-old GPS is useless. Paying for ACID durability on data you discard is the wrong tradeoff.
2. Why WebSocket over HTTP polling for location updates? ›
Polling at 4s interval across 500K drivers = 125K HTTP requests/sec. Each HTTP request carries full headers, auth tokens, and requires a TCP connection — even keep-alive connections have overhead. WebSocket: one connection per driver, established once at login, server pushes location data through it. Zero reconnect cost. Bandwidth drops by ~80%. Tradeoff: WebSocket is stateful — requires sticky sessions or Redis connection registry. Worth it at this scale.
3. Why SELECT FOR UPDATE when assigning a driver? Can't you handle this in application code? ›
No. With 10+ Matching Service pods, two pods can receive two different ride requests for the same driver simultaneously. Application-level checks ("check if driver is available, then assign") are not atomic — both pods read "available," both assign. This is a classic TOCTOU race condition. SELECT FOR UPDATE acquires a row-level lock in PostgreSQL: first transaction wins, second sees the lock and waits until the first commits, then sees status = "matched" and aborts. Database lock = the only correct solution across multiple pods.
4. Why TTL on driver location key instead of explicit offline marking? ›
Explicit offline marking requires the client to send a clean disconnect signal. But apps crash, phones die, networks drop — the clean disconnect never happens. TTL is self-healing: if the server doesn't hear from the driver in 30s, the key expires automatically. No cron job, no explicit cleanup, no zombie drivers staying "online" indefinitely. The heartbeat ping IS the keepalive. Stopping pings = auto-offline. This is the TTL-as-health-signal pattern.
5. Why dispatch to top 3 drivers simultaneously instead of sequentially? ›
Sequential: send to driver 1, wait 15s for response, then driver 2, wait 15s, then driver 3 = up to 45 seconds for a match. Rider abandons the app. Simultaneous: all 3 get request at once, first to accept = matched, others cancelled. Match time drops to under 5 seconds. Tradeoff: 3x notifications sent vs 1x. But push notifications are cheap (~0.01ms/notification), and matching speed is the core product metric. Always choose user experience over marginal notification cost.
6. Why Geohash and not QuadTree for SDE2 scope? ›
Geohash is Redis-native (Redis GEO uses it internally), requires zero custom code, and GEORADIUS handles proximity queries correctly by radius rather than by cell — the boundary problem is handled. QuadTree is operationally superior for highly uneven density (Mumbai vs rural Maharashtra), but requires a custom in-memory tree implementation, a service to maintain it, and logic to handle dynamic subdivision. At SDE2 scope, Geohash + Redis GEO solves the problem correctly. QuadTree is the Staff-level optimization when you have dedicated infra teams to maintain it.
7. What happens if two riders request the same driver at the same time? ›
Matching Service dispatches to driver from both ride requests. Driver accepts one. Trip Service processes: SELECT FOR UPDATE on driver row in PostgreSQL. First transaction commits, sets driver status = "matched" with rider A's trip_id. Second transaction reads status = "matched" → returns error to Matching Service → Matching Service re-runs matching for rider B with the driver excluded from candidates. Rider B gets the next nearest available driver. Total extra latency for rider B: ~100-200ms for the retry. No double assignment possible.
8. Why move completed trips to Cassandra instead of keeping everything in PostgreSQL? ›
Two reasons: (1) Scale — 20M trips/day = 7.3B trips/year. PostgreSQL B-Tree indexes degrade significantly past 100M rows per table. Query performance degrades. VACUUM and maintenance become expensive. (2) Access patterns change after completion — completed trips are append-only, read by user_id + time range. No joins, no updates. Cassandra's partition key (user_id, year_month) routes these queries directly to the right node without full scans. PostgreSQL excels at complex queries with joins — waste it on historical time-range reads.
9. Why is surge computed per geohash cell and not globally? ›
Demand/supply imbalance is geographic. Indiranagar (Bangalore) might have 10x demand over supply during an IPL match while 5km away in Whitefield there are 3x more drivers than riders. A global surge multiplier would overcharge Whitefield riders and undercharge Indiranagar riders. Geohash-cell surge (6-character precision ≈ 1.2km) correctly captures local demand. Each cell maintains its own demand/supply ratio, independently cached in Redis with 30s TTL.
10. How do you handle driver location data during a Redis restart? ›
Three-layer defense: (1) Redis AOF persistence — log every write to disk, replay on restart. Recovery time: seconds, not minutes. (2) Driver re-registration — drivers ping location every 4s. Even without AOF, full location state is rebuilt within 4 seconds as all drivers send their next heartbeat. (3) Kafka buffer — ride requests during the brief gap are queued in Kafka and retried when Redis recovers. The 4-second re-registration window means a brief matching gap, not a system outage.
11. Why is the Matching Service stateless even though it reads from Redis? ›
Stateless means: no per-request session stored on the server instance itself. Matching Service reads from Redis (external state store) and writes to PostgreSQL. It holds no in-memory state between requests. Any pod can handle any ride request — there's no "this request must go to pod 3." This is the definition of stateless: all state is externalized. Contrast with Location Service, which holds open WebSocket connections per driver — that IS stateful because the connection lives on a specific pod instance.
12. What happens if the Fare Service is down when a trip completes? ›
Trip Service marks trip as COMPLETED in PostgreSQL. Fare calculation event is published to Kafka (trip_id, distance, route, surge_multiplier). Fare Worker consumes this event, calls Fare Service (retries until available), writes fare back to trip record. Idempotency key = trip_id ensures even if Fare Worker runs twice, fare is calculated once. Rider sees "Calculating fare..." until Fare Service recovers. No trip is left without a fare — Kafka retention guarantees the event is processed eventually.
13. Why not use Google Maps API as the matching system? ›
Google Maps Distance Matrix API is for route calculation and ETA — it accepts origin/destination and returns driving time/distance. It cannot: (1) Index 500K live driver GPS positions in real time, (2) Answer "give me the 10 nearest available drivers to this point" in sub-100ms, (3) Handle 125K location update writes per second. The geo-indexing of live driver locations is the core technical problem of your system — it's what you're building. Google Maps is an external dependency for route ETA after the driver is matched. Never outsource your primary technical challenge to a third-party API.
14. How do you prevent a driver from being double-assigned across two concurrent ride requests? ›
Database-level row locking via SELECT FOR UPDATE on the driver's record in PostgreSQL. Flow: Matching Service sends accept request → Trip Service starts PostgreSQL transaction → SELECT driver WHERE driver_id = X FOR UPDATE → checks status = "available" → if yes, sets status = "matched" + creates trip record → commits. Second concurrent request for same driver → SELECT FOR UPDATE blocks until first transaction commits → reads status = "matched" → aborts with "driver unavailable" → Matching Service re-queries Redis GEO for next nearest driver. No application-level code can replicate this atomicity across distributed pods.
15. Why pessimistic locking over optimistic locking for driver assignment? ›
Optimistic locking works — on conflict, move to next driver on the cached top-3 list. But under surge, all 10 Matching Service pods get the same top-N driver list from Redis GEO. Simultaneous conflicts drain that list in milliseconds, and the Redis snapshot gets stale. Pessimistic lock blocks for 2–3ms and reads fresh state — cleaner under high contention. The real cost comparison: optimistic = cascading retries under load. Pessimistic = 2-3ms block. Under surge, pessimistic wins. Livelock risk with optimistic under high contention — pods keep retrying but never succeed as candidate list drains faster than they can assign.
16. Why is ride_requests table separate from trips table? ›
Not every booking request gets a driver. If we create a trips row on every booking, unfulfilled requests become garbage rows — no driver found, request timed out, but row remains. Two-table solution: ride_requests for short-lived pending state (30s TTL, then auto-expired), trips for confirmed rides only. Race condition still handled: atomic UPDATE on ride_requests WHERE status=PENDING — first driver to update wins, others see 0 rows updated. trips table stays clean with zero garbage rows and no cleanup job needed.
17. How does a ride request actually reach the driver's phone? Full path. ›
Matching Service → Redis registry lookup: driver_42 → Pod A (DNS). Matching Service → Kafka publish (key = Pod A). Pod A subscribes to its own Kafka partition. Pod A consumes message. payload.driver_id = 42. Pod A checks connectionMap.get(42) → WebSocket object. ws.send(ride_request) → Driver phone. On rebalancing: Kafka fires onPartitionsAssigned() callback → Pod A refreshes Redis registry for all its connected drivers. Self-healing, no manual update needed.
18. Why Kafka partition key = Pod ID (not Driver ID)? ›
Driver ID as key: partition is fixed, but the pod consuming that partition changes on rebalancing. Driver 42 is always in Partition 7, but after rebalancing, Pod D consumes Partition 7 — not Pod A where Driver 42 is actually connected. Pod ID as key: Matching Service looks up Redis (driver_42 → Pod A), publishes Kafka message with key=Pod A. Pod A subscribes to its own partition. Message arrives at Pod A exactly — where Driver 42 is connected. On rebalancing, onPartitionsAssigned() refreshes Redis: driver_42 → Pod A (fresh). Self-healing.
19. Why does Trip Service act as a central orchestrator (Saga pattern)? ›
Trip lifecycle spans multiple services: Matching (find driver), Location (en-route tracking), Fare (calculate), Payment (charge), Profile (rating update). Trip Service orchestrates all state transitions — REQUESTED → MATCHED → EN_ROUTE → COMPLETED. Each transition calls the relevant downstream service. On failure, Trip Service handles compensating transactions: payment failed → refund trigger, driver cancelled → re-match. This is the Saga orchestration pattern. Alternative is choreography (each service emits events, others react) but orchestration is clearer for a lifecycle with clear sequence and rollback requirements.
20. Why not store driver location in PostgreSQL/MySQL? ›
125K writes/sec. PostgreSQL max comfortable throughput is ~10–40K writes/sec under ideal conditions. Even at 40K, you are at 3x capacity immediately at peak. More importantly: location data is ephemeral — 30-second-old GPS coordinates are useless. Paying for ACID, WAL, disk flush durability on data you discard in 30 seconds is architecturally wrong. Redis GEO: in-memory (sub-ms), native TTL (auto-expires stale drivers), GEORADIUS query returns sorted nearby results in single command. SQL needs a full index scan + cleanup cron job. Wrong tool entirely.
21. What is Kafka consumer lag and why is it the best early warning metric? ›
Kafka lag = latest partition offset minus consumer's last committed offset. Normal: lag 0–10. Warning: lag 1000 (service slowing). Critical: lag 10000 (users about to feel it). The lag does not spike to 10K instantly — it grows. That growth trend gives you 10+ minutes to act before rider impact. Why better than CPU: CPU spike could be a normal burst. Growing Kafka lag means the service is systematically falling behind — it will cascade. CPU measures instantaneous state. Lag measures trajectory. SDE2 monitors trajectory, not state.
22. Driver loses network for 8 seconds (tunnel). What happens? ›
T=0: network drops. TCP connection to Pod B dies. T=5s: Pod B detects dead connection via TCP keepalive timeout. Pod B removes driver_42 from its local connectionMap. Does NOT touch Redis (TTL handles cleanup). T=0–8s: No heartbeat. Redis TTL counting down. But 8s < 35s → key still alive in Redis. T=8s: Driver reconnects. NEW TCP connection (TCP does not resume — it dies and is recreated). LB assigns to Pod D. Pod D onConnect() → connectionMap.set(42, newWS) → Redis.SET driver:42:pod = Pod-D EX 35. Heartbeat resumes. Self-healed. Old Pod B entry overwritten, not manually deleted.

Red Flags — Instant Score Killer

  • Using Google Maps API as the matching/geo-indexing system — outsources the core technical problem

  • Application-level locking for driver assignment instead of DB-level SELECT FOR UPDATE

Database Schema

8 tables — two separate for rides (short-lived requests + permanent trips). Storage split: PostgreSQL active, MySQL profiles, SQL partitioned/S3 historical.

1. riders

CREATE TABLE riders (
  rider_id    UUID PRIMARY KEY,
  name        VARCHAR(100),
  email       VARCHAR(255) UNIQUE,
  phone       VARCHAR(20),
  rating      DECIMAL(3,2) DEFAULT 5.0,
  created_at  TIMESTAMP DEFAULT NOW()
);

2. drivers

CREATE TABLE drivers (
  driver_id   UUID PRIMARY KEY,
  name        VARCHAR(100),
  email       VARCHAR(255) UNIQUE,
  phone       VARCHAR(20),
  vehicle_id  UUID REFERENCES vehicles(vehicle_id),
  rating      DECIMAL(3,2) DEFAULT 5.0,
  created_at  TIMESTAMP DEFAULT NOW()
);
-- NOTE: driver location NOT here → Redis GEO (125K writes/sec)

3. vehicles

CREATE TABLE vehicles (
  vehicle_id    UUID PRIMARY KEY,
  driver_id     UUID REFERENCES drivers(driver_id),
  make          VARCHAR(50),      -- Maruti, Honda
  model         VARCHAR(50),      -- Swift, City
  plate_number  VARCHAR(20) UNIQUE,
  category      ENUM('MINI','SEDAN','SUV')
);

4. ride_requests (SHORT-LIVED)

CREATE TABLE ride_requests (
  request_id  UUID PRIMARY KEY,
  rider_id    UUID REFERENCES riders(rider_id),
  status      ENUM('PENDING','MATCHED','CANCELLED','TIMEOUT'),
  source_lat  DECIMAL(10,7),
  source_lng  DECIMAL(10,7),
  dest_lat    DECIMAL(10,7),
  dest_lng    DECIMAL(10,7),
  created_at  TIMESTAMP DEFAULT NOW(),
  expires_at  TIMESTAMP             -- created_at + 30s timeout
);
CREATE INDEX idx_ride_req_status ON ride_requests(status);
CREATE INDEX idx_ride_req_rider  ON ride_requests(rider_id);

-- WHY SEPARATE: no garbage rows in trips table.
-- Unfulfilled requests auto-expire, trips = only confirmed rides.

5. trips (PERMANENT)

CREATE TABLE trips (
  trip_id       UUID PRIMARY KEY,
  request_id    UUID REFERENCES ride_requests(request_id),
  rider_id      UUID REFERENCES riders(rider_id),
  driver_id     UUID REFERENCES drivers(driver_id),
  fare_id       UUID REFERENCES fare(fare_id),
  status        ENUM('MATCHED','EN_ROUTE','PICKED_UP','COMPLETED','CANCELLED'),
  source_lat    DECIMAL(10,7),
  source_lng    DECIMAL(10,7),
  dest_lat      DECIMAL(10,7),
  dest_lng      DECIMAL(10,7),
  started_at    TIMESTAMP,
  completed_at  TIMESTAMP,
  created_at    TIMESTAMP DEFAULT NOW()
) PARTITION BY RANGE (created_at);  -- monthly partitions

CREATE INDEX idx_trips_rider    ON trips(rider_id);
CREATE INDEX idx_trips_driver   ON trips(driver_id);
CREATE INDEX idx_trips_status   ON trips(status);
CREATE INDEX idx_trips_created  ON trips(created_at);

-- Active trips: PostgreSQL (ACID, SELECT FOR UPDATE for driver assignment)
-- Trips older than 1yr: move to S3 archive

6. fare

CREATE TABLE fare (
  fare_id           UUID PRIMARY KEY,
  trip_id           UUID REFERENCES trips(trip_id),
  base_fare         DECIMAL(10,2),
  distance_fare     DECIMAL(10,2),
  surge_multiplier  DECIMAL(4,2) DEFAULT 1.0,
  total_fare        DECIMAL(10,2),
  currency          VARCHAR(3) DEFAULT 'INR',
  calculated_at     TIMESTAMP
);

7. payments

CREATE TABLE payments (
  payment_id       UUID PRIMARY KEY,
  trip_id          UUID REFERENCES trips(trip_id),
  rider_id         UUID REFERENCES riders(rider_id),
  amount           DECIMAL(10,2),
  status           ENUM('PENDING','SUCCESS','FAILED','REFUNDED'),
  payment_method   ENUM('CARD','UPI','CASH','WALLET'),
  gateway_txn_id   VARCHAR(100),    -- Razorpay/Stripe reference
  idempotency_key  VARCHAR(100) UNIQUE,  -- trip_id based
  created_at       TIMESTAMP DEFAULT NOW()
);

8. ratings

CREATE TABLE ratings (
  rating_id   UUID PRIMARY KEY,
  trip_id     UUID REFERENCES trips(trip_id),
  rated_by    UUID,   -- rider_id or driver_id
  rated_to    UUID,   -- rider_id or driver_id
  role        ENUM('RIDER','DRIVER'),
  score       DECIMAL(2,1),
  comment     VARCHAR(500),
  created_at  TIMESTAMP DEFAULT NOW()
);

Storage Split

PostgreSQL:   ride_requests, trips (active), payments, ratings
MySQL:        riders, drivers, vehicles
S3 Archive:   trips older than 1 year (via background job)
Why Two Tables for Rides? ride_requests = short-lived (30s TTL). Not every request gets a driver. trips = permanent, only created when driver accepts. Keeps trips table clean — no garbage rows, no cleanup job needed for unfulfilled requests.

Observability

Goal: know your system is about to fail before users feel it. Leading indicators over lagging indicators. RED method per service.

Core Philosophy Bad engineer: paged at 3 AM because riders cannot book. SDE2 engineer: paged at 2:45 AM because Kafka lag is trending up — fixes it before riders notice. The difference is leading vs lagging indicators.

RED Method — Apply to Every Service

R — Rate:     how many requests/sec is this service handling?
E — Errors:   what % are failing?
D — Duration: how long does each request take? (P50, P99)

1. Kafka Consumer Lag — Most Important Metric

ride-requests topic:
  Producer offset:  5000
  Consumer offset:  4990
  LAG = 10  ← normal

Alert thresholds:
  lag > 100    → Warning  (Matching Service slowing)
  lag > 1000   → Critical (has ~10 min before riders feel it)
  lag growing exponentially → service crashed

WHY better than CPU:
  CPU spike = could be normal burst
  Kafka lag growing = service falling behind → will cascade
  Lag gives you TIME to act before user impact.

2. Redis GEO — P99 Latency

Metric: GEORADIUS query latency
  P50  < 1ms   → normal
  P99  < 5ms   → normal
  P99  > 20ms  → WARNING — hot key or memory pressure
  P99  > 100ms → CRITICAL — Redis overloaded

What causes Redis P99 spike:
  1. Hot key    → all drivers in one geohash cell → single key overloaded
  2. Memory     → Redis near maxmemory → eviction overhead
  3. Large query→ GEORADIUS 50km radius → too many results
  4. Network    → Redis and Location Service in different AZs

3. Location Service — WebSocket Metrics

active_websocket_connections:  should be ~500K at peak
  Alert if: drops below 400K suddenly → mass disconnect event

connection_drop_rate:
  Normal: ~0.1%/min (drivers finishing trips)
  Alert if: > 1%/min → pod crashed or network partition

heartbeat_miss_rate:
  Alert if: > 5% drivers missing heartbeat → widespread connectivity issue

message_send_failure_rate:
  Alert if: > 0.1% → WebSocket push failing

4. Matching Service Metrics

match_success_rate:       Alert if < 85%
match_latency_p99:        Alert if > 5 seconds
rides_with_no_match:      Rising = driver supply problem
average_match_time:       Business health metric

5. Business Metrics (Don't Forget These)

rides_booked_per_sec:     Sudden drop = booking flow broken (revenue proxy)
average_match_time:       Rising = fewer drivers or matching slow
cancellation_rate:        Rising = driver declining or rider frustrated
rides_with_no_driver:     Rising = supply problem in certain geohashes

Observability Stack

Metrics collection:   Prometheus (scrapes every 15s)
Visualization:        Grafana dashboards (one per service)
Alerting:             AlertManager → PagerDuty → on-call
Distributed tracing:  Jaeger (traces API GW → Matching → Redis → Trip)
Log aggregation:      ELK stack (Elasticsearch + Logstash + Kibana)

Runbook — Matching Service Degrading

Alert fires: Kafka lag > 1000 on ride-requests topic

Step 1: kubectl get pods -n matching-service
        → Pods crashing? Check logs for OOM / exception

Step 2: Check Grafana: matching_service_processing_duration_p99
        → High? Redis GEO query slow → check Redis P99

Step 3: Check Redis memory / hot key analysis
        → MEMORY DOCTOR, OBJECT FREQ commands

Step 4: Scale horizontally
        kubectl scale deployment matching-service --replicas=10
        More consumers = faster lag drain

Step 5: If Kafka broker issue
        → Check broker health, leader election in progress?
Interview Answer — "How do you know system is healthy?" Three things: (1) Kafka consumer lag on ride-requests — if growing past 1000 messages, Matching Service falling behind, ~10 min before riders feel it. (2) Redis GEO P99 — above 20ms signals hot key or memory pressure. (3) Business metric: average match time — if rising above 8 seconds, something upstream degrading even if technical metrics look fine.
